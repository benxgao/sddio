# sddio 常见问题（中文速览）

> sddio 是给 coding agent 用的 spec-driven development：`SPEC`、`ADR`、`DISCUSSION`、`FLOW` 四种 Markdown 跟代码一起提交，让代码背后的判断跨会话存活。

这是英文版 [FAQ](faq.md) 的中文速览，每条只留结论和边界；两版措辞有出入时以英文版为准。问题顺序与英文版一致，包括那些其实是反对意见的问题。

## sddio 是什么？

一个小命令行工具，加上一个它想帮你养成的习惯：把关于项目的判断留在仓库里、代码旁边，而不是留在关掉就没的聊天窗口里。它记四种 Markdown，跟代码一起提交，再给 agent 留一句"开会话时先看看这个"。MIT，Node ≥ 18，一个 devDependency。就这么点东西，没有更聪明的花样。

## 什么是 spec-driven development？

先写清这次改动必须成立什么，再写让它成立的代码，这样需求本身能被单独拿出来讨论，不用对着 diff 猜。这个想法比这些工具老得多。sddio 只是把它用在项目层面，而不是单个特性上：一套长期有效的需求、决定和未决问题，大致跟着 `HEAD` 走。不为每个特性造一棵新的 spec 树。那一步，通常是大家悄悄放弃的地方。

## 支持哪些 coding agent？

只要它能读仓库里的文件，基本都行：Claude Code、Codex、Cursor、Copilot，本地模型也可以。它不写 agent 专属配置，也不进 agent 的配置目录，只通过 `AGENTS.md` 注册，多数 agent 本来就会瞄一眼这个文件。支持 skill 的 agent，可以用 `npx sddio skill --print` 给它一个很短的路由。你的工具这些都不支持也没关系，文件就是 Markdown，自己读也读得动。

## SPEC、ADR、DISCUSSION、FLOW 有什么区别？

大致这么记：SPEC 是必须成立什么；ADR 是为什么这样做（包括被否掉的那个方案）；DISCUSSION 是还没定的事，趁还开着的时候写下来，那时候写最便宜；FLOW 是此刻在做的事。前三个是知识，FLOW 是游标，扔掉重写都不碍事。

## sddio 是 skill 吗？和 Claude Code skills 什么关系？

不是 skill，是仓库约定加一个 CLI。确实附带一个很小的 `SKILL.md`，但那是路由、不是规则：确认 `.sddio/context/instructions.md` 在，教 agent 用 `grep` 列条目、命中处只读前后约 25 行，格式细节交回上下文层。两者不冲突：skill 管"怎么做"，sddio 记"这个项目已经决定了什么"。因为 skill 里没有自己的规则，升级上下文层不会把它弄坏。没有 skill 的 agent 就用 `AGENTS.md`，损失很小。

## 这不就是多了几步的 AGENTS.md 吗？

一半是，而且这一半值得承认：只要一本规则手册，`AGENTS.md` 就够了，sddio 也只往里面加三行。差别在另一半：会烂的那一半。手写的 `AGENTS.md` 年复一年声称同样的事，漂了也没人发现；`sddio_workspace/` 每次开会话跟 `HEAD` 对一次，被最近提交弄旧的那几条，才是 agent 要重读的。要是这种"变旧"从来没坑过你，那就留着单个文件，挺好的。

## 它是自己跑，还是要我手动维护？

它不会自己跑，这是故意的：没有守护进程、没有 git hook、没有后台任务、没有网络请求。它在 agent 打开会话、读到 `AGENTS.md` 的时候才起作用；那个"提交检查"是它接下来照做的一句话，不是有东西在盯着你的仓库。手动只有两处：`init` 加一次粘贴；升级包之后，粘贴它打印的对账提示词。别的都不排期。代价也说清楚：要是你的 agent 根本不读 `AGENTS.md`，或者你用的编辑器里没有 agent，那就什么都不会发生，文件安静地躺着，正确，但没人用。

## 会不会覆盖我的 AGENTS.md 和已有文件？

不会，这一点它挺小心。不加 `--force` 时只写缺的文件；已有的 `AGENTS.md` 原样留着，只在 `<!-- sddio:begin -->` 和 `<!-- sddio:end -->` 之间追加三行，重跑是原地更新，不会再堆一份。唯一有意替换的是 `.sddio/`，它归包所有，每次 init 和升级都会刷新。`sddio_workspace/` 只有 `--force` 会动，而 `--force` 是把它重置成空种子。那个参数是用来重新开始的，不是用来合并的，别拿你在乎的目录去试。

## 是不是每次会话都多塞一堆上下文？

会多一点点，设计上也在尽量让这个"一点点"是真的：启动读四个短文件、跑一次提交检查，详细说明等真需要了再加载，条目是清单短句而不是段落，skill 要求先 `grep` 定位、只读命中附近，而不是整本读一遍。没有公开的 token 基准，所以别信任何具体数字，包括我们说的。真正值得比的是它替掉的东西：让 agent 读代码重新推一遍，推得更差，而且每次都得从头来。

## 单人项目值得吗？

得看这个项目活多久，我宁可这么说，也不硬卖。周末脚本：不值得。四种文件花的注意力比省下的记忆还多，仓库里就是这么写的。它开始划算，是工作隔一阵又回来的时候：三周后回来、两个 agent 先后动同一块代码、同一个取舍解释到第三遍，自己都听出语气里的疲惫。触发条件是重复，不是团队规模。一个人做两年，比一个只交付一次的团队更需要它。

## 会取代我的 issue 跟踪吗？

不会，而且它当不好。`FLOW` 是个游标：此刻在做什么、agent 下次不能丢什么。没有 backlog、没有指派、没有优先级、没有通知，没有会来敲你的东西。issue、迭代、路线图，留在团队每天早上本来就打开的那个工具里。`FLOW` 一旦长得像任务列表，多半是被派了不该它干的活。

## 会把代码发出去吗？

不会。没有账号、没有服务端、没有遥测、没有分析、没有更新检查。它只在你指定的项目目录里读写文件，自己不跑任何 git 命令。那两个新文件夹要不要提交、什么时候提交，你按自己的节奏来。不用了就把 `.sddio/` 和包删掉，没东西留在那儿往回打电话。

## 现有项目、monorepo 能用吗？

能，而且多数人正是这么来的。`init --dir <path>` 可以指向任意目录，仓库根或单个包都行，各自得到一套 `.sddio/` 和 `sddio_workspace/`。在已有项目上，第一条提示词会让 agent 从现有的代码、测试、配置和文档里推出一个最小 SPEC，而不是请你坐下来把做过的事重讲一遍。它总会推错一些，你改回来，那个改动就是第一件值得提交的东西。

## 不用了会怎样？

不会怎样，这正是没做锁定的意思。`SPEC`、`ADR`、`DISCUSSION`、`FLOW` 就是仓库里的普通 Markdown。删掉 `.sddio/` 和包，`sddio_workspace/` 依然可读、可 review、可 diff。没有导出，没有迁移，也没有东西扣着你的笔记不放。

## 和 Spec Kit、OpenSpec 的区别？

那两者规划特性：开工时被调用，按特性建一套结构来装计划。sddio 记录项目：一套长期有效的需求与决策，会话开始时按上次之后移动过的提交对账，没有按特性的命令要记。哪个更好，看你手上是什么活：一个全新的大特性，按特性走的工具挺合适；项目漫长的中段，真正一直坏掉的是记忆。三者都不收集使用数据，sddio 什么都不发。详细对照在 [README 那一节](../README.zh-CN.md#sddio-和-spec-kitopenspec-有什么区别)，2026 年 10 月核过。

## 不用 CLI 行不行？

行，而且是故意的：四个问题本身就是产品，CLI 只是围着它搭的脚手架。抄进 Notion、PR 模板或团队 wiki，收益拿到大半，什么都不用装。CLI 替掉的是忙起来最容易跳过的那一步：开会话时先把文件打开，把被最近提交弄旧的那几条更新掉。这一步很无聊。正因为无聊，交给工具比交给一个本来打算做的人更靠谱。
