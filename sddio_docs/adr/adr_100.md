## Two-root layout: `.sddio/` machine layer and `sddio_docs/` human layer

- `.sddio/` — machine/config layer: instructions, schemas, routes, `config.json`.
- The layer carries no project-specific content: preferences and a roadmap are the user's, not the package's.
- `.sddio/` is owned by `@sddio/cli`; overwritten on init, updated on upgrade (SPEC-006).
- `sddio_docs/` — human workspace: `spec/`, `adr/`, `discussions/`.
- `sddio_docs/` is owned by the user and their coding agents.
- The CLI never overwrites it (SPEC-003).
- ADR entries live in `sddio_docs/`, not in `.sddio/`.
- Both roots are committed (SPEC-007).

### Alternatives

- Single root — `.sddio/` holds the workspace, or `sddio_docs/.sddio/`: rejected.
  - Only gain: one fewer top-level directory.
  - Merges CLI-owned and user-owned files, so safe overwrite rules are hard to express.
  - Higher risk of accidental overwrites.

### Consequences

- Every consumer repository carries two top-level directories.
- Tools must know which root is writable.
- Ownership is explicit: template updates can overwrite `.sddio/` without risking user artifacts.
- The machine/config layer stays out of daily work.

## `@sddio/cli` implementation stack

- Language: TypeScript, compiled by `tsc` alone — no bundler.
- Output: `dist/`, published as ESM.
- Argument parser: `commander` permitted, despite the "avoid unnecessary dependencies" preference.
- `engines.node`: `>=18.0.0`.
- `bin` runs the prebuilt `dist/` output, so `npx @sddio/cli` needs no build step on the consumer side.

### Alternatives

- Plain JavaScript: no build step, but loses type safety across a growing command surface.
- Bundler: adds tooling for no benefit at this package size.

### Consequences

- Build output must be published with the package.
- ESM-only raises the minimum Node version to 18.

## Initialization copies templates from the installed package

- `sddio init` copies templates from the installed package into the consumer repository — copy once.
- Templates are never fetched remotely.
- Templates are never read from the consumer's own repository.
- Paths resolve relative to the package root.

### Alternatives

- Reference `node_modules` at runtime: rejected.
  - Couples artifacts to an installed version.
  - Breaks when the package is removed or upgraded.
- Fetch templates remotely: rejected. Adds a network dependency; blocks offline initialization.

### Consequences

- Consumer copies drift from later releases.
- Drift is handled by CLI upgrade plus reconciliation (SPEC-006), not by live references.
- Shipped instructions can change between versions without silently retargeting existing projects.

## FLOW and reconciliation are rollout plans, not artifact types

- FLOW files and reconciliation records are rollout/execution plans, not a persistent artifact type.
- No schema file, no IDs; slug-based file names.
- Not referenced from `routes.md` or otherwise by the spec system.
- FLOW files need not follow the FLOW template exactly.
- Reconciliation records live in `flow/reconciliation/`.
- Completed records move to `flow/completed/` as `date_commit_5digits.md`.
- Coding agents may start a FLOW without prior approval; user confirmation is preferred.

### Alternatives

- Fifth artifact role (`RECON-*` prefix, schema, routes entry): rejected.
  - Records are short-lived execution state.
  - The structure adds maintenance cost without durable retrieval value.

### Consequences

- `routes.md` and `entries.md` cover only SPEC, ADR, DISCUSSION.
- FLOW tracking stays outside the spec system, so the spec layer stays limited to confirmed knowledge.
- Reconciliation history is kept as completed records, not a queryable artifact type.

## The shipped context is generated from the repository root `.sddio/`

- `packages/cli/templates/` is a build artefact, not source.
- `npm run sync` recreates `templates/.sddio` from the root `.sddio/` before every build and pack.
- `templates/` is git-ignored; the root `.sddio/` is the single source of truth for the context layer.
- The workspace is not templated; `sddio_docs/` is declared in `lib/workspace.ts`.
- Declaration contents: directories plus empty seed files.
- No placeholder content ships; directories `npm pack` cannot carry are created explicitly.

### Alternatives

- Committed copy under `packages/cli/templates/`: the previous approach.
  - 17 duplicated files drifted from the root copy on every instruction change.
- Symlink into the repository root: does not survive `npm pack`.
- Files embedded in a generated TypeScript module: works, but hides them from review and from `diff`.

### Consequences

- The context cannot drift between the repository and the published package.
- Building from a partial checkout fails fast instead of shipping an empty template.
- `sync` asserts `.sddio/context/instructions.md` exists.
- `templates/` must never be committed; `.gitignore` enforces that.
- The `files` field still packs it into the tarball.

## The cursor stores two commits, not one

- Superseded by `ADR-013`. `previousCommit` is gone: it was the parent of the knowledge commit, which git computes.

- `lastProcessedCommit` alone cannot distinguish appended work from rewritten history.
- An amended, rebased, or reset tip replaces the commit the cursor points at.
- A second commit — the parent — survives that rewrite and anchors the diff.
- `previousCommit` is always `lastProcessedCommit^`, never an older cursor value.
- Classification is by reachability: equal, ancestor, present, missing.

### Alternatives

- One commit and `git log` inspection: fails once the object is gone or the clone is shallow.
- A `HEAD..` range string instead of SHAs: unreadable in review, brittle across rebases.
- Storing the whole processed range: unbounded size for a two-line gain.

### Consequences

- `config.json` carries two SHAs per consumer repository.
- A rewritten tip costs one commit of re-examination, not a full rescan.
- Initialisation and upgrade ship `null` for both, so the first run baselines.
- `sync-templates` clears the cursor, otherwise this repository's SHAs would ship.

## Evidence travels with the rule; ceremony does not

- A shipped rule that can be checked names its command, or states that it is judgement.
- A rule that goes unexecuted for three releases is deleted rather than restated.
- Imported: a command per checkable claim, a before-number per metric, a marker for written-but-unproven,
  and an index that makes an entry findable.
- Not imported: readiness scores, closing phases, reviewer gates, the kanban — measured 0 of 7
  completions, or outside what sddio says it is.

### Alternatives

- Import the source project's plan template wholesale — 596 lines, 43% governance prose, four closing
  phases at 0 of 7.
- Ship a `check` command — a maintenance surface for rules a `grep` already covers; the evidence from the
  source project is that a command typed at a known moment was enough (`lint:logs`: 182 files, 0
  violations, no CI).
- Leave the rules to each project's `AGENTS.md` — the state this ADR replaces: 623 shipped lines, 0
  mentions of verification.

### Consequences

- The instructions grow by roughly 40 lines, capped at 700 in total.
- A consumer gains a word for the commonest real state: written, and not yet proven.
- The retirement criterion applies to these rules too — three ignored releases and this ADR is the thing to
  delete.
- `sddio check` and `check --claims` ship, reversing the alternative above: drift against `HEAD` and the
  commands a bullet claims turned out cheap to run. Whether an entry still says the right thing stays
  outside any command, and `docs/distribution.md` keeps that gap written down.

## The registry is the only install channel

- `@sddio/cli` reaches users through npm: `npx`, `devDependency`, later global. Nothing else installs it.
- Which of those a repository uses, and how its version is recorded, is ADR-017: `npx` with the version in the command.
- No marketplace plugin, no agent-side installer, no second copy of `dist/` and `templates/`.
- An agent installs procedure; sddio ships files. A skill alone hands over the four questions, which the README already gives away.
- `npx` runs in an empty directory, so "no npm project" was never the barrier. Node ≥ 18 is, and no channel removes it.

### Alternatives

- A plugin bundling `dist/` and `templates/` — 36K, no runtime dependency, so it would work; rejected for a second version clock (the plugin's CLI against a workspace scaffolded by another) and an install path with no publish review or tarball check.
- A skill-only package pointing at `npx` — nothing to bundle, but saves one command and still needs Node.
- A single-file `sddio.mjs` download — no registry, no discovery, no update path.

### Consequences

- `docs/distribution.md` remains the release checklist; no channel to add to it.
- Node ≥ 18 is a stated cost of every install. A compiled binary is the only way past it and is not planned.
- Revisit when a consumer repository without Node asks, or a marketplace gains a gate comparable to the npm token plus a required reviewer.

## sddio stores knowledge; a hook decides when it is updated

- Superseded by `ADR-014` for the default hook and `ADR-013` for the cursor. The knowledge/plan boundary below stands.

- `FLOW` is removed. sddio keeps `SPEC`, `ADR` and `DISCUSSION`; work in progress belongs to flow-trail.
- `config.json` carries `reconcileCursor` (the two commits) and `hooks` (who calls reconciliation, and when).
- A hook is a declaration: sddio never calls one. `init` installs the chosen hook, then forgets it.
- `flow-trail` is the default hook: a board of folders in git, calling sddio when a card closes.
- The `hooks` array survives an upgrade; the rest of `config.json` is replaced.
- Supersedes `ADR-004`: a plan is not knowledge, and two homes for it would drift.

### Alternatives

- Keep a `FLOW` artifact — two tools would each hold a plan, and the agent would have to know which is current.
- Let the agent self-trigger at session start only — covers reading, not writing, so knowledge goes stale between sessions.
- A daemon or a scheduler — breaks the no-server property for a job that runs a few times a day.
- Install every hook `init` offers — writes files the user did not ask for; one question, one choice.

### Consequences

- How current the knowledge is depends on a third-party tool being installed and used.
- A repository declaring `hooks: []` goes stale until someone runs the check; nothing is wrong, just old.
- `init` reaches the network and runs a remote installer when a hook is chosen — the only place sddio does.
- Work tracking has a second home, so the README has to say which question belongs where.

## An entry earns its place by being falsifiable

- A `SPEC` bullet must be something a command could fail on; a sentence no check could contradict is an `ADR`, or nothing.
- Every entry ends with `Not in the code:` — why reading the repository would not give you the fact.
- A layout, a file list, a flag's behaviour, or a copy of a shipped instruction is a citation: point with `refs`.
- The existing entries were written before this gate and gain the line when next touched.
- Applied here: 15 `SPEC` entries became 10, 95 bullets became 32, and 263 lines became 144.

### Alternatives

- One collection with a `kind:` field — one lifecycle for two kinds of truth; requirements are corrected, decisions are superseded.
- Adopt flow-trail's findings shape wholesale (Saw / Means / Cost / Not in the code / Cited by / Check) — six lines per entry taxes the ten entries a year that need it.
- Leave `SPEC` as a mirror of the implementation — what it had become: a second copy that drifts, 20 of 95 bullets naming a path or a flag.

### Consequences

- Writing an entry costs one more sentence, and about half the candidates fail it.
- A `SPEC` entry that cannot name its check is now suspect rather than comfortable.
- `ADR` keeps the reasons, `SPEC` keeps the assertions; neither repeats the other's content.

## The baseline is the newer of two commits

- The baseline is whichever is newer: `reconcileCursor.lastProcessedCommit`, or the newest commit that changed `sddio_docs/`.
- The knowledge commit wins by default, so writing the cursor into that same commit does not leave the workspace one behind.
- Amend safety comes from recomputation, not from a second anchor: the baseline is derived from `HEAD`'s own history on every run.
- A cursor that no longer exists falls back to the knowledge commit, reported as `recovered`; there is no `rewritten` state.
- A commit that changes only `.sddio/` is not counted: the context layer documents itself.

### Alternatives

- Two commits (`lastProcessedCommit` + `previousCommit`) — `previousCommit` is the knowledge commit's parent, which git already computes; keeping it turned an amend into a permanent `rewritten`.
- Compare with `HEAD^` unconditionally — the tip's own files leave the worklist, so the newest change is never named.
- Delete the cursor and always derive — loses "reconciled, nothing to write", the one case where no commit records the work.
- A ref to the knowledge tree — content-addressed and amend-proof, but local-only and one more concept to explain.

### Consequences

- `config.json` carries one commit, and an upgrade keeps it.
- A rebase, `gc`, or a fresh clone degrades to the knowledge commit instead of an error.
- An out-of-band knowledge edit moves the baseline forward, and with it any code committed since the last reconcile.
- Two ancestry checks replace the state table; neither can fail in a way that produces a false alarm.

## Approve nothing on the first run

- `init`'s default hook is `none`; choosing `flow-trail` is one answer away, and installs it.
- The only network call in the product moved from the default path to an explicit choice.
- `--yes` takes the default, so a script cannot install a remote installer by accident.
- `SECURITY.md` says `init` writes inside the project and runs no git command; that is now true of every path a first run takes.

### Alternatives

- Keep `flow-trail` the default — a first run pipes an unpinned script from `HEAD` into `bash`, writes `~/.flow-trail` and uses git, while the security page says none of that happens.
- Remove `flow-trail` entirely — it is the hook this repository uses, and dogfooding it is how it gets tested.
- Default to `flow-trail` with a warning — a warning on the first screen is a prompt to click through.

### Consequences

- A new user finishes `init` with an empty `hooks` array and runs the check themselves; `AGENTS.md` already tells their agent to.
- The boundary in `ADR-011` stands: knowledge here, plans there. It is no longer installed by default.
- `--no-install` is no longer needed for CI; it stays for declaring a hook without fetching it.

## The schema version describes the entry, not the release

- `config.json` `schemaVersion` is the shape of a SPEC, ADR or DISCUSSION entry, and it is `1`.
- A release that changes rules, wording or commands leaves it at `1`.
- It moves to `2` when an entry's frontmatter or section shape changes; the `.schema/` files move with it.
- It agrees with the `<!-- schema version: 1.0.0 -->` header the collections already carry.
- What an upgrade left behind is never decided by this number: `init` compares the directory with it.

### Alternatives

- Bump per release — it read 1, 2, 3 across three changes of rules, and no consumer could say what 2 meant.
- A release version beside it — two numbers, and the second would be checked by nothing.
- Drop the field — the schema files already carry the version, but a machine needs one place to read.

### Consequences

- A 0.2.x repository's `3` becomes `1` on its next `init`; nothing reads it, so nothing changes.
- Staleness is detected structurally from now on, which is why `init` reports orphans instead of migrating.
- A real format change is one number, the schema files, and a release note that names what broke.
- Not in the code: nothing reads this number, so only a decision can say what it is for.

## Removing an orphan is not re-initialising the workspace

- `--prune` removes the files this version no longer ships, and nothing else.
- `--force` keeps its meaning: refresh everything, and reset the `sddio_docs/` seeds to empty.
- They are separate because the orphan line made `--force` the obvious answer to a routine question.
- The hint under an orphan names `--prune`, so the safe command is the one already printed.

### Alternatives

- Make `--force` stop resetting the seeds — that is the documented way to start over, and a test asserts it.
- Remove orphans with no flag — a run that deletes files should be asked for, not inferred from a version bump.
- Tell people to delete the file themselves — correct, and silent to anyone who reads the output instead of the docs.

### Consequences

- Two destructive flags; the safer one is the newer name, and the help lists them in that order.
- `--force` still removes orphans, being a superset, so a script that used it keeps working.
- A pruning run leaves no trace of what it dropped; the commit is the record.
- Not in the code: the two meanings collide only when a report recommends the destructive one, which no type can say.

## The command is the lockfile

- sddio runs from npm's cache with the version inside the command: `npx -y @sddio/cli@<version>`.
- `init` writes that command into the `AGENTS.md` block from its own `package.json`, so the pin cannot be mistyped.
- A repository with no `package.json` — Python, Go, Rust — is a first-class case, not a workaround.
- Upgrading is `npx -y @sddio/cli@latest init`: it rewrites `.sddio/` and the version in the block together.
- `-y` because a session has no tty; npm's install prompt is a hang, not a question.

### Alternatives

- A `devDependency` plus a lockfile — real integrity, but it puts a `package.json` in projects that deliberately have none, and it was the only documented path before this.
- A bare `npx @sddio/cli` — no file either, but it floats with `latest`, so a session changes tool versions mid-project.
- A global install — machine-level and short, but it cannot be pinned per repository, and it is untested here.
- Publishing an unscoped `sddio` alias — the shorter command, rejected: a second package to publish in step with this one.

### Consequences

- The first run needs the registry, which a committed dependency did not. An air-gapped machine cannot run sddio.
- `AGENTS.md` changes on every upgrade, so a version bump appears in a consumer's diff: that is the reviewable record a lockfile would have been.
- A 0.3.x project that keeps its devDependency is not broken; the block names a version `npx` can fetch.
- The pin is only as good as the file. An agent that ignores `AGENTS.md` and runs `@latest` moves the tool under the project, and nothing detects it — judgement, not a check.
