## Two-root layout: `.sddio/` machine layer and `sddio_workspace/` human layer

Artifacts are split across two roots at the repository root:

- `.sddio/` — machine/config layer: `config.json`, `instructions.md`, `instructions/`, `principles.md`, `preferences.md`, `roadmap.md`, `routes/`. Owned by `@sddio/cli`; may be overwritten on init and updated on upgrade (SPEC-006).
- `sddio_workspace/` — human workspace: `spec/`, `adr/`, `discussions/`, `flow/`. Owned by the user and their coding agents; never overwritten by the CLI (SPEC-003).

ADR entries are recorded in `sddio_workspace/`, not in `.sddio/`. Both roots are committed (SPEC-007).

### Alternatives

A single root — either `.sddio/` holding the workspace, or `sddio_workspace/.sddio/` — was rejected. It reduces the number of top-level directories, but merges CLI-owned and user-owned files, which makes safe overwrite rules hard to express and raises the risk of accidental overwrites.

### Consequences

Every consumer repository carries two top-level directories, and tools must know which root is writable. In exchange, ownership is explicit, so template updates can overwrite `.sddio/` without risking user-authored artifacts, and the machine/config layer stays out of the way of daily work.

## `@sddio/cli` implementation stack

The CLI is written in TypeScript, compiled to `dist/` with `tsc` alone (no bundler), and published as ESM. A small argument parser such as `commander` is permitted despite the "avoid unnecessary dependencies" preference.

`engines.node` is `>=18.0.0`. The `bin` entry runs the prebuilt `dist/` output, so `npx @sddio/cli` works without a build step on the consumer side.

### Alternatives

Plain JavaScript avoids a build step but loses type safety across a growing command surface. A bundler adds tooling for no benefit at this package size.

### Consequences

Build output must be published with the package, and the ESM-only choice raises the minimum supported Node version to 18.

## Initialization copies templates from the installed package

`sddio init` copies the templates shipped in the installed package into the consumer repository (copy-once). Templates are never fetched remotely and never read from the consumer's own repository; paths are resolved relative to the package root.

### Alternatives

Referencing templates in `node_modules` at runtime would couple consumer artifacts to an installed package version and break when the package is removed or upgraded. Fetching templates remotely would add a network dependency and prevent offline initialization.

### Consequences

Consumer copies drift from later releases. Drift is handled by the CLI upgrade plus reconciliation path (SPEC-006) rather than by live references, so shipped instructions can change between versions without silently retargeting existing projects.

## FLOW and reconciliation are rollout plans, not artifact types

FLOW files and reconciliation records are rollout/execution plans and are not a persistent artifact type. They carry no schema file, no IDs, and slug-based file names, and they are not referenced from `routes.md` or otherwise by the spec system. FLOW files need not follow the FLOW template exactly.

Reconciliation records live in `flow/reconciliation/` and move to `flow/completed/` named `date_commit_5digits.md`. Coding agents may start a FLOW without prior approval, though user confirmation is preferred.

### Alternatives

Treating reconciliation as a fifth artifact role — with a `RECON-*` prefix, a schema, and a routes entry — was rejected: the records are short-lived execution state, so the structure would add maintenance cost without durable retrieval value.

### Consequences

`routes.md` and `entries.md` cover only SPEC, ADR, and DISCUSSION. FLOW tracking stays outside the spec system, so the spec layer stays limited to confirmed knowledge, and reconciliation history is kept as completed records rather than a queryable artifact type.
